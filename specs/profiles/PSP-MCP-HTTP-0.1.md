# PSP MCP HTTP Mediation Profile 0.1

Status: **project draft, pending review**, September 22, 2026. Identifier: `PSP-MCP-HTTP-0.1`.

This opt-in extension of [PSP-MCP-DISPATCH-0.1](PSP-MCP-DISPATCH-0.1.md) adds a bounded subset of MCP [2025-11-25 Streamable HTTP](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports), [authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization) and [cancellation](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/cancellation). It preserves PSP Core §11/§22.5 and CDL §5/§7 baselines. It does not establish full MCP/OAuth conformance or complete Topology B/C mediation.

## 1. Identity and credentials

Hosts MUST configure the exact endpoint outside model/RPC inputs. HTTPS uses certificate-chain and hostname validation; there is no verification-disable option. A custom CA bundle changes trust roots, not hostname checks. Explicit plaintext development mode accepts only literal loopback hosts (`127.0.0.1`, `localhost`, `[::1]`). URLs with user information, query strings, fragments, noncanonical serialization or unsupported paths are rejected. No redirects, proxy environment configuration or automatic request replay is supported.

The server's host authentication callback receives the token and configured resource URI. It MUST validate issuer, intended audience/resource, expiry/revocation and scopes, returning an authenticated tenant/subject principal or null. Authentication runs before session lookup and again before response release. A MCP session identifier is a routing handle, never a credential. Server self-reported name/version is an additional mismatch check, not remote authentication.

The downstream token supplier receives only the fixed resource URI. Hosts MUST supply a distinct resource-specific credential; they MUST NOT pass through the caller's token. These libraries consume host-obtained access tokens. OAuth authorization-server discovery, browser authorization, PKCE, registration, token acquisition/refresh and scope escalation remain host integrations, not implemented OAuth client flows. The resource-server adapter publishes protected-resource metadata with configured HTTPS authorization-server URLs and advertises its metadata URI in 401 challenges. Invalid tokens are rejected without initiating a downstream request.

## 2. Inbound transport and state

The framework-neutral adapter validates duplicate headers, Host, Origin, media type, Accept, protocol version, strict UTF-8/JSON and size before dispatch. It rejects every supplied Origin; browser/CORS access is unsupported. Only the configured MCP path is routed. GET on that path returns 405: no standalone SSE stream. POST accepts one JSON-RPC request or notification, without batches or server-to-client responses. Accepted notifications return 202 with an empty body and never execute tool calls. Successful requests return a complete bounded JSON response. DELETE terminates an authenticated owner's transport session and flags any active request for cancellation. It does not cancel or delete the durable PSP workflow session.

Successful initialization issues a random UUID transport session bound to tenant/subject, separate from the host-selected durable workflow session. The initialized protocol is pinned to 2025-11-25. A missing version header can use that pinned session version; an explicit other version is rejected. Unknown, expired or foreign-owner session IDs return 404; missing IDs on ordinary requests return 400. A new explicit initialization is required after expiration; the client adapter reports `PEER_SESSION_EXPIRED` and closes, leaving recovery to the host without replaying an operation.

Sessions are process-local with an absolute configured lifetime (1–3,600,000 ms), a global capacity (1–1,024), at most one ordinary in-flight request per session and at most 4,096 distinct request IDs (safe integers or strings of at most 128 UTF-8 bytes). Duplicate IDs return 409; exhausting the ID budget invalidates the session. Busy sessions return 409. Restart invalidates all transport sessions. Sessions are not persisted because their active calls, cancellation flags and initialized dispatchers cannot be restored safely from SQLite alone. Load-balanced deployments need sticky routing or a separately specified distributed transport-state service.

The host opens and closes a request-local tool service. Its workflow selector and policy controls MUST come from authenticated host state, not request `_meta`. Every gate and workflow writer for an owner MUST share the dispatch profile's coordinator. Python SQLite connections MUST be opened in the executing worker; the transport never disables SQLite thread checks. A stored MCP dispatcher retains lifecycle/identity only; each invocation uses an immutable request-local credential/service context.

## 3. Downstream requests and response buffering

The HTTP client uses the same pinned discovery, explicit host approvals, exact input/output schemas, capability-source union, affinity and dispatch/release policy gates as the stdio client. The entire discovered catalog is rechecked before and after tools/call. These checks detect observed drift, not a malicious peer's false declarations or changes between requests. Hosts MUST keep the approved endpoint behavior stable. Atomic remote revision preconditions and hot discovery updates remain unsupported.

Clients accept application/json and finite text/event-stream POST responses. SSE comments, event IDs, retry fields and empty priming events can precede a single `message` response. The client buffers the entire finite stream before parsing/releasing its JSON-RPC result. Multiple messages, server requests, notifications, unexpected event types, invalid IDs, truncated events, non-UTF-8 data and oversized responses fail closed. Resumable streams, reconnect polling, standalone subscriptions and progress events are unsupported; no SSE bytes bypass the gate. A peer that leaves a response stream open hits the exchange deadline. Downstream text/metadata is never relayed: only validated object structuredContent reaches the release gate, and proxy text is regenerated from that object with local level-5 provenance.

## 4. Bounds and cancellation

JSON bodies and complete serialized responses are limited to 1 MiB; the client also counts SSE framing toward that limit. Header collections are limited to 8 KiB at the adapter boundary. Network hosts MUST additionally enforce connection/header-read quotas, TLS termination and worker limits. The supplied Node handler bounds body ingestion to five seconds; the Python handler requires Content-Length (no chunked request uploads), bounds reads, preserves duplicate headers and omits request logging. Neither helper is a production serving stack.

Each downstream exchange has an independent wall/monotonic deadline of 1–30,000 ms, including credential acquisition, connection, writes and reads. Python isolates blocking I/O in a daemon worker and shuts down its socket on cancellation; an uninterruptible DNS or host credential callback can outlive the call, but cannot deliver output or send a request after observing cancellation. Hosts MUST bound their callbacks and resolvers. Clients close on faults and never silently retry. Normal idle close attempts DELETE; failed connections can leave an expired remote transport session for server cleanup.

Only the authenticated transport-session owner can send `notifications/cancelled` for its current request ID. Cancellation runs concurrently with the ordinary request, ignores unknown/completed IDs and cannot cancel initialize. The server passes a cancellation predicate combining explicit cancellation, transport-session expiry and the configured call deadline to the host service. Gate adapters MUST use it. Late completion produces an empty HTTP 204 with no JSON-RPC result; no governed content is released. The host callback must cooperate to stop work promptly; Python threads and arbitrary callbacks are not forcibly preempted. A socket disconnect alone does not cancel a request.

On downstream timeout or host cancellation, the client closes the response connection and attempts a separate bounded cancellation notification (at most one second). It suppresses late output regardless of notification delivery. Notification delivery is best effort, not proof of remote termination. Cancellation cannot retract disclosed inputs or already executed effects. Only explicitly approved read-only tools are admitted; mutating tools, exactly-once effects, outbox recovery and distributed owner locking remain separate work.

## 5. Evidence

[Shared HTTP scenarios](../../conformance/vectors/dispatch/http-0.1.json) compare status, decision, actual tool-spy counts and released output. Real mixed-language HTTP/TLS checks exercise both certificate and hostname rejection, distinct credentials, finite JSON/SSE, redirects, drift, malformed results, cancellation and complete caller/proxy/tool chains. Package checks exercise installed public exports. These are scoped synthetic implementation results, not security effectiveness, production readiness, independent review or complete conformance.
